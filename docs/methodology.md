# Assessment by PROMPTS — Methodology

> **Language:** [Español](metodologia.md) · English

## Foundations

### The problem of assessing code in the age of AI

Since ChatGPT appeared (November 2022), assessing code has a fundamental problem:

1. **Code can be generated** - A student can ask ChatGPT "write an ETL pipeline with Spark" and get working code.
2. **Code does not reveal learning** - Two students can submit identical code, one copying it and the other understanding it.
3. **Manual review is inefficient** - Reviewing PRs line by line when the code is generated makes no sense.

### The solution: assess the process

Instead of assessing the **product** (code), we assess the **process** (how you got there):

- The prompts you used with the AI
- The questions you asked
- The mistakes you made and how you solved them
- Your final understanding of the project

## System Components

### 1. The PROMPTS.md file

This is the main deliverable. It contains:

**Part 1: Real prompts**
- At least 3 prompts copied VERBATIM
- With typos, informality, everything
- A screenshot of each one

**Part 2: Final blueprint**
- A technical summary generated by the AI at the end
- Shows that you understood what you built

### 2. GitHub Action to close PRs

Automatically:
- Detects when someone opens a PR
- Leaves a comment explaining the system
- Closes the PR

### 3. Evaluation script

Automatically analyzes:
- Whether PROMPTS.md exists
- Number of documented prompts
- Whether there are screenshots
- Whether there is a blueprint
- Word count (a proxy for effort)
- Suspicious patterns

## Cheating Detection

### "Cleaned" prompts

Real prompts carry human traits: typos ("how do i geT..."), informal language ("help me
with..."), basic questions ("what is spark"). Prompts written after the fact tend to be
perfectly spelled, very technical, and error-free.

### Copy of the example

If the instructor gives an example with countries X, Y, Z, the system detects whether
someone reused the same countries.

### Incoherent blueprint

If the blueprint describes technologies that do not appear in the code, something is off.

See [`anti-cheating.md`](anti-cheating.md) for the full detail. Every signal is a **prompt
to look**, never a verdict.

## Workflow

### For the student

```
1. Fork the repository
2. Work with any AI
3. Document prompts WHILE working
4. Take screenshots of the important prompts
5. At the end, ask the AI for a blueprint
6. git push to your fork
7. Done (no PR)
```

### For the instructor

```
1. Wait for the deadline
2. Run: python evaluar_prompts.py
3. Review the generated report
4. Manually verify the REVIEW cases
5. Publish grades
```

1. A GitHub repository

3. A list of student usernames

## Privacy and consent

This system asks students to publish their prompts and screenshots in a public fork.
Before applying it:

- **Informed consent**: explain that the work will be public and obtain the student's
  consent; offer a private alternative (a private repository or submission through the
  virtual classroom / LMS) for those who do not want to expose their work.
- **Personal data in screenshots**: screenshots may contain a name, email, or the
  student's account interface. Tell them to **crop/hide** any personal data before
  uploading.
- **Regulation**: comply with your institution's data protection (GDPR in the EU, FERPA in
  the US). Pseudonymize where possible.
- **Retention**: agree on how long the work stays public and how to withdraw it on the
  student's request.

## Scope: the people you know and the people you don't

The system cuts review time and raises productivity, but it rests on an assumption
worth making explicit. Within a course or a development team, whoever assesses
**knows their people**: they recognize a student's or collaborator's voice in their
prompts just as they would recognize how that person writes code, and the coherence
between the process and the person is verifiable almost at a glance. In that regime,
the automated triage frees time precisely because the underlying judgment rests on
prior knowledge.

The nature of the problem changes when the proposal comes from **someone they do not
know** —an external contribution to a public (open-source) project, which is, not by
accident, the scenario pull requests were created for. There, reading the prompts is
not enough: one must read **between the lines** how the reasoning was built,
**test** the contribution, and decide whether to accept or reject it by applying the
experience and knowledge of the craft. That decision retains an **irreducible
subjectivity**: it cannot be automated, foreseen, or eradicated, and it is exactly
the part that we, as humans, still have to manage. Assessment by prompts shifts and
reduces the work of review within an already-established relationship of trust —the
classroom, the team—, but it **does not remove human judgment** where that trust
does not already exist. Acknowledging this limit does not weaken the method: it
automates the triage, not the responsibility to decide.

## Limitations

- The "cleaned prompts" detector is heuristic and **evadable** (a student can ask the AI
  to add typos). Treat the alerts as signals to review in person, not as verdicts.
- The efficacy evidence comes from a single deployment (see README); it does not replace a
  study with learning data, a false-positive rate, and validity analysis.
